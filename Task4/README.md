# Пояснение по выполнению задания

1. Так как авторы не предоставили примеров таблиц DB CRM, то было решено использовать базу данных из задания 1 и таблицу user_profiles, где записи
появляются через CDC при авторизации пользователя через Keycloak, если он еще отсутствует в таблице. Соответственно, Debezium отслеживает изменения
в таблице user_profiles, а KafkaEngine в Keycloak подписывается на топик с событиями изменения данной таблицы. Таблица с показаниями датчиков
создается и заполняется при инициализации контейнера с ClickHouse. В качестве витрины я
сделал представление, объединяющее данные датчиков и информацию из профиля. Для реализованного в рамках предыдущих заданий
отчета по показаниям датчика конкретного пользователя эта информация избыточна, но для других отчетов, если они будут строиться по всем пользователям, может понадобиться.
2. Для витрины я создал обычное представление, а не материлизованное и вот почему:
   а) MV в ClickHouse - это insert-триггеры, которые активируются при вставке данных в таблицу. У нас есть динамическая вставка, только
      в таблицу user_profiles, а таблица с показаниями датчиков (emg_sensor_data) заполнена изначально. Данные, которые были в таблице до создания MV,
      не обрабатываются новым MV. Но даже если создать представление до заполнения emg_sensor_data, то это не решит проблему (см. след пункт)
   б) Можно создать MV с ключом POPULATE и тогда в него попадут данные из emg_sensor_data, а так как user_profiles еще не заполнена,
      то все поля получаемые из user_profiles, будут NULL. Кроме того, изменения только в таблицах справа от JOIN (user_profiles) не будут триггерить обновление MV.
      А так тестовый кейс состоит в том, чтобы после поднятия сервисов и авторизации под пользователями, по которым есть показания датчиков, мы получили
      корректные данные в представлении, то самый лучший вариант - это обычное представление, которое строится по актуальным данным.
